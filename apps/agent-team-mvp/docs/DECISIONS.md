## 2. 実装で確定させた事項

### D-001 実装言語とリポジトリ配置

**決定:** TypeScript のモジュラーモノリスとして `apps/agent-team-mvp/` に新規実装する。

**根拠:** 要件定義書 §8「技術要件」がアーキテクチャ・UI・API・データ・LLM・チャット・テストの各層を
TypeScript 前提で指定しているため。本リポジトリの既存 CLAUDE.md は Python を規定しているが、
それは Virtus(8 体エージェント)および Officina に対する規約であり、本 MVP は
エージェント構成・スコープ・技術要件がいずれも異なる別プロダクトである。
両者が混ざらないよう、ディレクトリを分離した。

**影響:** ルートの Python プロジェクト(`src/`, `tests/`, `pyproject.toml`)には一切変更を加えない。

---

### D-002 判定を LLM に委ねない

**決定:** 根拠の突合、権限判定、リスク区分、状態決定、承認 scope の検証は
すべて決定論のコードで行う。LLM には「文章化」と「指摘の追加」だけを任せる。

**根拠:** G2(根拠付与率 100%)と G3(承認記録なしの外部行為ゼロ)は受入条件であり、
モデルの気分に依存させると、受入条件そのものを検証できなくなる。
評価セット 20 件が提供元・モデルを問わず再現するのはこの設計による。

**影響:**
- 業務改善エージェントが LLM の書いた事実行を採用するのは、その文に含まれる
  数値・日付・決定事項がすべて紐づく根拠に含まれる場合だけ。含まなければ原文の根拠へ差し替える。
- 品質/承認エージェントの LLM は指摘を追加できるが、指摘を消すことも承認することもできない。

---

### D-003 状態の優先順位に `human_review_required` を追加

**決定:** FR-020 が列挙する 9 状態に加えて `human_review_required` を持つ。
優先順位は `needs_clarification` より弱く、`needs_revision` より強い位置に置く。

**根拠:** FR-022 の「3 回目で自動ループを止める」は QA の判定結果ではなく
ワークフロー側のループ遮断であり、9 状態のいずれとも意味が異なる。

---

### D-004 承認より根拠不足が弱いことの扱い

**決定:** FR-021 の優先順(`approval > revision`)をそのまま実装する。
外部行為を含む案件で根拠が不足していても、状態は `awaiting_approval` になる。

**根拠:** FR-021 は受入条件であり、優先順を勝手に入れ替えない。

**補償策:** 未解消の指摘と根拠付与率を承認パケットの `constraints` に必ず載せる。
承認者はカードの制約欄で「根拠付与率 92.0%(未達分は承認者が確認する)」を見てから判断する。

---

### D-005 承認されても MVP は外部送信しない

**決定:** `external_email.send` / `crm.record.commit` / `storage.delete` / `storage.overwrite` などは、
承認されても `ManualHandoffAdapter` が受け、`handed_off_to_human` として人間実行へ引き渡す。

**根拠:** 要件定義 §2「MVP に含めない: 外部メールの自動送信、CRM 確定更新、削除・上書き」。
承認フロー(FR-023 / FR-032 / G3)は完全に動かしつつ、実際の外部作用は MVP の外に置く。

**影響:** 実行範囲を広げるときは、手順書 E-2 の「外部送信・CRM 確定更新の追加」に従い、
経営・業務・セキュリティの明示承認とロールバック試験を行う。

---

### D-006 却下された案件の状態

**決定:** 承認権者が却下(`rejected`)した案件は、`stage = closed` とし、
`state` は `human_review_required`(自律的な処理を行わない)とする。

**根拠:** FR-020 の状態集合に「却下」に対応する状態が無い。
自動処理を止めて人間の管理下に置く、という意味を最も近く表す状態を選んだ。
却下の事実は `approval_decisions` と監査イベント(`approval.decided` / `rejected`)に残る。

---

### D-007 カードにワンタイム値を載せない

**決定:** 通知カードのボタン値には `request_id` と `card_version` だけを入れる。
ワンタイム値(nonce)は、サーバーが詳細モーダルを開くときに `private_metadata` へ入れる。

**根拠:** FR-031「カードに実行権限そのものを含めない」を、
「カードだけを再送しても最終確定できない」状態として実装するため。

---

### D-008 Slack Bolt を使わない

**決定:** Slack 連携は Bolt を使わず、Block Kit の JSON 生成と
`v0=HMAC-SHA256(v0:{timestamp}:{rawBody})` の署名検証を直接実装する。

**根拠:** FR-034 の署名・タイムスタンプ検証はテストで示すべき受入条件であり、
フレームワークの内部に隠れていると回帰テストが書けない。
`verifySlackSignature` は単体テストで、改ざん・別シークレット・時刻ずれを直接検証している。

---

### D-009 「古い資料」の扱い

**決定:** 更新日が `SOURCE_STALE_AFTER_DAYS`(既定 180 日)より古い資料は、
限界(`limitations`)として記録し、その資料由来の根拠の信頼度を 0.5 に下げる。
参照可能な資料が**すべて**古い場合は `hold_for_decision` で止める。

**根拠:** 手順書 C-2 工程 3 の停止条件「古い資料」を、
「一部が古い」と「全部が古い」で分けた。前者で毎回止めると実務が回らず、
後者を素通しすると古い前提のまま成果物が作られる。
