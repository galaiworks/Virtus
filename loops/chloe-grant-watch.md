# Loop Contract: chloe-grant-watch(クロエ 助成金週次モニタ)

- 作成日: 2026-08-03
- オーナー(人間): ガライ(galaiworks)
- 自律度レベル: **L1(報告のみ)** ← 初期値。昇格は人間のみが判断

---

## 0. 適性判定(A-1)

| 軸 | 判定 | 根拠 |
|---|---|---|
| 反復性 | ✅ | 助成金の公募・締切は継続的に変動し、週次で追わないと取り逃す |
| 検証可能性 | ✅ | `chloe_weekly_check.py` が決定論的に JSON を出力し、Level ≥ 3 で非ゼロ終了する |
| 経済価値 | ✅ | 締切 1 回の取り逃しで 7.5 万〜200 万円の損失。手動チェックは毎回約 30 分 |

3 軸すべて YES → ループ化する。**セッション横断ループ(定期トリガー)** として設計する。

> ⚠️ セッション内 cron は使わない。リモート実行環境のコンテナは非アクティブで回収されるため、
> 週次スケジュールが数日で消える。GitHub Actions のスケジュール実行でリポジトリに常設する。

---

## 1. Goal(再帰的ゴール)

- **ゴール**: galaiworks が対象になり得る助成金・補助金を取り逃さない状態を維持する。
- **完了条件(機械判定可能)**: 毎回の実行で以下がすべて満たされること。
  - 監視対象すべての適格性判定が完了し、`candidates` / `excluded` に分類されている
  - 締切が判明している候補について残日数が算出され、エスカレーション判定が実行されている
  - 実行結果が状態ファイルへ書き戻されている
- **恒久ループである理由**: 制度は毎年変わり続けるため終端はない。1 回の実行単位で上記条件を満たせば「そのパスは完了」とする。

## 2. Trigger(起動条件)

- **起動方式**: GitHub Actions `schedule`(cron)+ `workflow_dispatch`(手動実行)
- **頻度・タイミング**: 毎週月曜 08:00 JST(= 日曜 23:00 UTC / `0 23 * * 0`)
- **「やることが無い」場合の挙動**: 何もせず正常終了。レポートを artifact に残すのみで通知しない。

## 3. Stop(停止条件・三重ガード)

| ガード | 値 |
|---|---|
| 反復上限 | **1 実行 = 1 パス**(内部リトライなし)。ジョブタイムアウト 10 分 |
| 差分停止 | 直近 3 回のパスで候補・締切・エスカレーションに変化がなければ通知を出さない(実行自体は継続し artifact のみ残す) |
| 予算上限 | **0 トークン**(LLM を呼ばない決定論スクリプトのみ)。GitHub Actions の実行時間のみ消費 |

- **上限到達時の挙動**: 状態ファイルに現況を書き出し、未完了として終了。ジョブを失敗させて人間へ通知。

## 4. Verify(検証・Maker-Checker)

- **Maker(生成役)**: `scripts/chloe_weekly_check.py`(決定論。LLM 非依存)
- **Checker(検証役)**: 以下の 2 段構え。Maker とは分離されている。
  1. **自動**: `pytest tests/test_incorporation_*.py`(103 件の回帰テスト)。ロジック変更でスクリプトが壊れていないことを保証する。
  2. **人間**: 提示された締切・要件を**公式一次情報で照合**してから行動する。二次情報の締切をそのまま信じないことが、このループ最大のリスク統制。
- **完了の証跡**: JSON レポート(artifact)+ pytest 実行ログ + 状態ファイルの差分
- **Checker 不合格時**: テストが落ちた場合は**最大 0 回リトライ**(即停止)。ロジックの誤りを黙って回し続けないため。ジョブ失敗として人間へ通知。

## 5. Permission(権限境界)

自動で許可:
- [x] リポジトリの読み取り
- [x] `pytest` の実行
- [x] ループ状態ファイル(`loops/state/`)への進捗追記
- [x] JSON レポートの artifact 保存

禁止(人間の明示許可が必要):
- main / 本番への push・マージ
- **外部送信**(Slack / LINE / メール / 申請フォームへの入力・送信)
  → L1 では通知も自前で送らない。**ジョブ失敗による GitHub 標準通知**のみを使う
- 助成金の**実際の申請・提出**
- `brain/customers/` 配下(顧客の財務データ)の読み書き
- 削除操作 / 課金の発生する操作

## 6. Memory(外部メモリ)

- **状態ファイル**:
  - 機械可読: `loops/state/chloe-grant-watch-state.json`(制度の締切・ステータス。**公開情報のみ**)
  - 人間可読: `loops/state/chloe-grant-watch-STATE.md`(必須 4 項目)
- **必須 4 項目**: 完了したこと / 進行中のこと / 次にやること / ブロッカー
- **読み書きルール**: 各実行の冒頭で読み、末尾で更新する。会話コンテキストに状態を溜めない。
- **⚠️ データ分離**: 顧客固有の財務データ(役員報酬・売上・家族構成)は `brain/customers/`(gitignore)に留め、
  このループの状態ファイルには**入れない**。ループが扱うのは公開情報の制度データのみ。

## 7. Escalate(エスカレーション)

- **人間を呼ぶ条件**:
  - エスカレーション **Level 3 以上**を検出(締切 7 日前で未着手 / 社保の空白 / 実態なき家族給与)
  - Checker(pytest)が失敗
  - contract 解釈に迷い
  - 状態ファイルと実態の drift 検出(締切を過ぎているのにステータスが更新されていない等)
- **通知先・方法**: **ジョブを失敗させ、GitHub 標準の失敗通知**でリポジトリオーナーへ届ける。
  L1 では外部送信が禁止のため、Slack 等への自前投稿はしない。
  詳細は artifact の JSON レポートで確認する。

## 昇格の考え方(手順 C)

| レベル | このループでの内容 | 昇格条件 |
|---|---|---|
| **L1(現在)** | 該当候補と締切を報告するのみ。行動は人間 | — |
| L2 | 申請書類のドラフト生成まで(Guardian 95 点通過が前提)。提出は人間 | L1 で提案の採用率が安定し、誤検知が許容範囲に収まること |
| L3 | 申請の提出まで自動 | **採用しない**。補助金の申請は虚偽記載が不正受給に直結するため、提出は恒久的に人間ゲートとする |

> L3 を意図的に封じているのが本ループの特徴。「無人化できるから無人化する」ではなく、
> 誤りが法的責任に直結する操作は人間に残す。
